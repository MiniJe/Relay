# RLY-UX-R-001 — Operator workflow research

**A8 research lab · 29 September 2026 · advisory evidence for A4**

Relay should organize the interface around the next operational decision: who owns this signal, who has actually been reached, what response is underway, and what customers can currently see. The strongest improvement opportunity is continuity between those decisions, rather than adding more dashboard panels.

This report does **not** define Relay 0.3 scope, qualify Relay 0.2, or change production behavior. A4 owns the product/architecture specification; A3 owns qualification. All implementation in this research branch is under `docs/`. No production API, persistence, authorization, delivery, or public projection was modified.

## Incident creation: count the outcome, not just the modal

### Counting method

`A` is one command activation: button, link, checkbox, confirmation or submitted slash command. `F` is completing a text field or choosing a select value, counted once regardless of keystrokes. Focus clicks, scrolling, reading, network waits, login and initial configuration are excluded and must be observed separately in a human trial. Start locations and assumed defaults are specified; counts cannot be compared without them.

“Ready” means four independently inspectable outcomes: incident exists; accountable person known; responders have a stated notification/receipt outcome; current internal/public exposure understood. Creation alone is not “ready.” A provider accepting a request never establishes that a human read it.

Avoidable Relay friction: the Overview CTA navigates to another CTA; severity defaults differ between manual and alert-derived creation; service context is carried forward but command responsibility is invisible; public scope must be mentally reconstructed from components and pages. A global creation entry point could save one navigation action. More important: the operator should finish the existing three-action alert path with the four outcomes legible.

## Incident command: continuous context versus secondary detail

| Information | Keep continuously available | Secondary view / disclosure |
| --- | --- | --- |
| Commander and current owner | Named commander; current technical owner; unassigned state; explicit handoff action | Full roster, role history, access policy |
| Responders | Invited/accepted/working counts and any failed page; strongest known receipt fact | Per-channel attempts, retries and raw provider errors |
| Severity and lifecycle | Text severity with definition; current lifecycle; one explicit transition action | Full severity policy and historical timestamps |
| Affected services | Short named set with impact uncertainty; service owner link | Complete component mapping and dependency details |
| Tasks | Next blocking action, owner, due/overdue state and remaining count | Full checklist and completed work |
| Timeline | Latest meaningful decision and last update time | Complete chronological audit, filters and raw events |
| Communications | Internal/public separation, last public text/status, audience, next promised update and delivery result | Earlier messages, templates and subscription setup |
| Runbooks | Relevant runbook title; running/failed step when applicable | Full instructions and execution evidence |
| Linked alerts | Count, newly unacknowledged/failed members and direct entry | Raw payload, correlation history and source metadata |
| Next update | Absolute time with timezone, due/overdue wording and responsible person | Cadence configuration/history |

On mobile, “continuously available” means a compact, reachable summary/action strip, not a sticky 400 px header. Avoid forcing the full table above into the first screen. The prototype demonstrates the information model but uses a flowing mobile header; persistent mobile action placement remains a follow-up experiment.

Use “Acknowledge alert,” “Assign owner,” “Page backup,” “Create incident,” “Add internal update,” and “Publish public update.” Each verb describes a different effect. “Escalate” alone is ambiguous between paging another person and declaring a coordinated response. Command responsibility must not be confused with authorization: assigning commander must never grant a workspace role.

## Alert handling at 5, 50 and 500

| Load | Operator question | Recommended behavior | Acceptance experiment |
| --- | --- | --- | --- |
| 5 | Which needs me, and why? | All rows visible; clear raw urgency, age, owner and receipt; detail alongside list. No mandatory grouping. | Identify unowned signal and acknowledge without opening an unrelated page. |
| 50 | Which ones are mine or not reaching anyone? | Needs response / Mine / Failed delivery / Suppressed views; search by service/ID; preserve position; page-scoped selection and compact detail. | Find a known late-list alert, inspect its route, then return without losing filters or selection context. |
| 500 | Is urgent work hidden by noise or limits? | Server-filtered cursor queue, explicit total/query count, stable ordering, bounded rendering, oldest unowned and delivery-failure access. Related groups disclose count, first/last seen, worst state and grouping basis. | Find alert 499 and an older failed page; acknowledge exactly selected objects while new alerts arrive. No silent 200-record cutoff or false “all quiet.” |

Triage stages should remain distinguishable: ingest durable record → evaluate route → attempt delivery → human acknowledgement → assign/hand off → correlate → explicitly declare/link incident → investigate → resolve. Acknowledgement cancels only what the backend says it cancels; provider requests already in flight can still arrive. Show that limit without losing the action result.

Suppression must name its **scope** (this user, this alert/group, or upstream rule), reason, author, expiry and resume behavior. Keep suppressed work findable; surface a new member whose severity or delivery state changes. Never label suppressed signals healthy. For a storm, preview the exact count and members of bulk changes; return per-item success/conflict/failure and retry only failed items. The prototype implements page-scoped acknowledgement and fixture suppression; it does not implement production suppression semantics.

Separate deduplication (same source identity repeated), grouping (related signals presented together), and incident linkage (operational coordination). Grouping should show why and allow correction without deleting source evidence. Similar titles alone do not prove one cause. Do not silently acknowledge new alerts because older group members were acknowledged. These are proposed contracts for A4 to assess, not changes to Relay's current intake semantics.

For live traffic, show “12 new alerts” and let the operator insert them, or append safely; never move the row under an action. Preserve pending edits across connection loss. Display stale age and retry state; successful write receipt should be authoritative before a destructive-looking action disappears. A cursor API, revision handling, conflict recovery, aggregate counts and authorization remain production design work.

## On-call ergonomics

“Who gets paged now?” requires a **service/route and timestamp**, not just a global avatar. Show service → matched route → escalation policy → currently resolved responder, with evaluation time and usable channel configuration. Separately label the responder actually selected for an existing alert. A handoff changes future resolution; it does not rewrite the historical recipient.

Show next handoff as both duration and exact time in a named timezone, with incoming and outgoing people. A “covered schedule” must not imply a usable contact method or a human receipt. Distinguish no schedule, disabled schedule, no participant, outside a rotation, stale evaluation, skipped integration, failed delivery and acknowledgement.

An override should preview affected window, replacement, return-to-rotation behavior, overlaps and any gap it closes or creates. Absence is not coverage: a requested replacement remains “awaiting acceptance” until the applicable policy establishes coverage. Relay currently has administrator-configured overrides, not a full absence/request-coverage workflow. Do not imply that merely recording leave transfers a page.

Schedule confidence comes from evidence: current evaluation, next shifts, gaps, active override, configured channels, last test result and a route simulation. A green avatar alone is insufficient. Keep ordinary responder actions small—inspect now/next, ask for cover, take over—with full rotation authoring a secondary administrative view. A4 should decide whether self-service cover belongs in scope.

## Public status boundary: preserve it at every transition

The existing invariant is sound: public projection omits internal summary/notes, operational timeline, responders, alert payloads, routing, schedules and integration secrets. The audit fixture confirms internal note and summary canaries are absent. The issue is **intent legibility**, not evidence that the tested canaries leaked.

Current behavior is important: `publicIncident()` includes title, severity, lifecycle, timestamps and affected public component IDs. An incident associated with a public page's components can appear publicly with **zero public messages**. The fixture confirms its title appears before publishing a message. Creating/editing affected components, changing lifecycle and resolving can therefore change public state. The Resolve button warns about immediate public change; selecting Resolved in the lifecycle dropdown bypasses that particular confirmation. Review of message text alone is incomplete protection against accidental exposure of a sensitive title or an unintended state change.

Proposed interaction contract:

1. Create an internal incident from an alert with no implicit public component selection. Keep an explicit “Not published / visible on …” summary based on actual server projection.
2. Compose customer text in a separate field set. Do not prefill raw alert text, internal summary, hostnames, notes or identities into public drafts. Separate public title is a prototype hypothesis; current Relay has one canonical title.
3. Review the exact destination page(s), public audience, title, message, component/state, timestamps/next promise, and notification consequence. State whether the operation merely saves a draft or makes content visible. Missing destination is a recoverable configuration problem, not successful publication.
4. Submit the reviewed revision with server authorization, tenant/reference validation and an explicit allowlist projection. UI omission is never the security boundary. If state or destinations changed since preview, refresh/review the difference; do not silently publish a different projection.
5. After success, show persistent published receipt and customer preview. On failure, keep the draft and state “not published.” On network ambiguity, check operation status before retry to avoid duplicate publication. Conflict and idempotency details belong to A4.
6. Apply the same consequence preview to component association, public-affecting lifecycle/severity changes and resolution. Never treat internal resolution as proof of customer communication delivery.

There are two viable candidates for A4: **retain the canonical public projection and review every public-affecting change**, or **separate public publication/lifecycle from internal command state**. The latter permits an independently reviewed public title and recovery update, but adds reconciliation and stale-public-status risks. The prototype deliberately explores the second, labels the divergence, and leaves public Investigating visible after internal resolution until an explicit public update. This is UX evidence requiring an architecture decision, not an approved schema change.

Required future security tests include anonymous projection, tenant crossing, viewer/responder/admin authority, every public-changing mutation path, malicious markup, retries, conflict after preview, newly linked components/pages, and no accidental copying from operational payloads. The prototype's canary assertion checks its local projection only; it cannot establish these server guarantees.

## Navigation and visual direction

Candidate grouping for testing: **Operate** (attention overview, Alerts, Incidents, On-call, Status communication) and **Configure** (Services/public components, Teams, Routing/policies, Integrations/access). Keep stable deep links. “Paging activity” could become an Alerts view while remaining globally reachable for delivery troubleshooting. “Status pages” setup could become a secondary part of Status communication.

This is consolidation of entry points, not removal of domain concepts. Services and public components are not redundant data; routing policies and their executions are not the same record. Dashboard/Alerts/Escalations repeat summaries, and On-call repeats now/next facts; consolidation should remove duplicate navigation while preserving contextual evidence.

Use neutral surfaces, restrained borders, 13–14 px body text, 12 px secondary text, approximately 36–44 px controls, and spacing to separate decisions. Color supports explicit state words. Reserve stronger visual emphasis for unowned work, failed delivery and overdue communications. Tables/lists carry density; cards should group distinct decisions, not wrap every number or member. No decorative gradients, animated metrics, large operator heroes or compulsory AI summaries.

## Prototype evidence

Open [the prototype](prototypes/operator-workflow/index.html) directly in a browser, or run the loopback server in the README. It runs without dependencies or a Relay login. All people, services, times and receipts are fictional; refresh or changing the fixture volume resets state. It makes no network requests to Relay or providers and stores nothing durably.

Implemented journey: alert → acknowledge → create incident → commander/response context → internal note → separate public draft → exact review → publication/failure/retry → internal resolution → post-incident review owner/date/follow-up. Additional experiments include assign, page-backup preview, page-scoped bulk acknowledgement, explicit fixture grouping and manually ended fixture suppression. Runbook content is inspectable, with no command execution.

The first keyboard test exposed focus leaving the modal's last control; an explicit focus loop was added and the test rerun. The prototype is evidence to interrogate, not an accessibility certification.

Known prototype limits: a single active incident; simulated invite/provider outcomes; no collaboration/auth/RBAC; fixed fixture clock; no server query/load test; no automatic suppression timer; grouping is a display annotation without production correlation or ungroup history; no draft survival across reload; no real runbook execution or external postmortem ticket. The mobile inbox has a bounded scrolling queue and detail below it; whether that is better than a dedicated detail route needs human testing. Public communication is lower in the flowing mobile command view even though its state remains in the header. These limitations must not be mistaken for approved product behavior.

## Mobile and accessibility considerations

Mobile priorities: identify the signal, acknowledge, see owner/receipt, page backup, add a short note and review a public update. Schedule authoring and raw payload inspection are secondary. Use a stacked alert summary with actions in the same visible region; no horizontal journey to the rightmost table column for acknowledgement. Preserve back navigation, query and scroll. Test an on-screen keyboard, landscape, long localized text, low connectivity and interrupted publication, not only screenshot widths.

Keep touch targets at least 44 px in this prototype's mobile layout; use text labels alongside status colors. Do not rely on hover or tiny icons. With zoom/reflow, collapse secondary metadata rather than suppress primary decisions. A sticky action row must not obscure focused controls or reserve most of a small screen.

Accessibility recommendations: semantic headings and landmarks; `for`/`id` or wrapping labels; named dialogs and menu expanded state; logical focus order, trap and return; keyboard equivalents for every action; no global single-letter shortcuts inside text controls; an optional shortcut disable/remap path in production; persistent inline errors plus restrained live announcements. Keep high contrast for text and focus, honor reduced motion and avoid live queue movement. Color contrast, 200/400% zoom, NVDA/VoiceOver and real touch interaction still need specialist/manual testing. Automated containment and control inventory are only partial evidence.

## Recommendations and decision requests for A4

| Recommendation / confidence | Why it is worth considering | Dependency / question owned by A4 |
| --- | --- | --- |
| Make public exposure a first-class state; **high** | Source and anonymous fixture show messages are not the only public-affecting path. | Keep canonical coupling with comprehensive review, or create an independent publication model? What resolves stale public state? |
| Expose command responsibility and page receipt separately; **high** | Commander exists but is invisible; historical target, acceptance and ownership are easily conflated. | Which fields can be surfaced from current semantics, and which acknowledgement/handoff contracts are new? |
| Design Alerts as a bounded searchable work queue; **high** | Current 200-item slice cannot represent 500 alerts honestly. | Query/pagination/count contract, consistency under ingest and authorization for bulk operations. |
| Move creation forms behind explicit actions; **high** | Existing rules are below y=1120 desktop; mobile operational content is displaced. | Mostly presentation, but role-aware visibility and deep-link behavior need consistency. |
| Retain current routing/delivery audit details, summarize first; **high** | Existing attempts/jobs are useful evidence; a redesign must not remove them. | How to make failures, stale reads and partial lists explicit without making operators interpret storage terms? |
| Test compact command tasks, next-update ownership and linked signals; **medium** | Documentary patterns converge; prototype makes the vertical workflow legible. | New task/deadline/runbook semantics and post-incident responsibility are potential scope, not approved requirements. |
| Consolidate navigation around operation/configuration; **medium** | Several duplicated summaries and split setup/execution paths. | Validate discoverability with operators before removing existing entry points. |
| Add self-service coverage/absence workflows; **lower until tested** | Current overrides are administrative and absence can create ambiguity. | Permission model, acceptance semantics, gap preview and operational need versus scope cost. |

Suggested next study, for whoever owns validation: recruit 5–8 representative operators across on-call, commander and communications roles; include an infrequent responder and an assistive-technology user. Counterbalance baseline/prototype order using identical fixtures. Tasks: declare with owner and receipt understood; find the older failed alert among 500; handle a handoff/override; separate private diagnosis from a public message; recover failed publication; resolve and assign follow-up. Observe exact actions, backtracking, wrong-owner assumptions, incorrect audience predictions, hidden records and draft loss. Ask participants to explain who is being paged and what customers can see, rather than asking whether the interface looks clean.

Proposed research gates, not release scope: all participants can identify the next page target and whether delivery is confirmed; no participant unintentionally publishes internal diagnosis; the older failed signal remains discoverable at 500; public failure never appears as success; keyboard-only users complete the core path; mobile acknowledgement requires no horizontal table scrolling. Report actual completion times and errors only after those trials. A4 can accept, reject or sequence these candidates against architecture and product constraints.
